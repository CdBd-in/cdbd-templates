# MD-05. 페이지 유형 판정

## 1. 입력

- **설명 글** — 유저가 확인·수정을 끝낸 페이지 설명 1개
- **목적** — 유저가 확정한 목적 문구 1개
- **추가 항목** — 유저가 **켠 칩만** (문구 · 추가할 섹션 목적 · 들어갈 자리)
- **타겟** — 타겟 문구 1개 ＋ 유저가 고른 라벨
- **주제 코드** — 앞 단계에서 자동 판정한 주제(25개 중 1개 · **화면 노출 ❌**) → 그 주제의 **조립 레시피**를 펼친다
- **조립 레시피** — 그 주제의 섹션 목록. **관문 ②(챕터 수)·④(카드 수)를 재는 자**다

## 2. 출력

페이지 유형 1개 (원페이지 / 멀티페이지)

## 3. 규칙

- 유저에게는 **통보형** — 고르게 하지 않고 정해서 보여준 뒤 `바꾸기`만 둔다

### 3-A. 4관문 — 앞에서 걸리면 거기서 끝

| | 묻는 것 | 판정 |
|---|---|---|
| **0** | 목적이 **알림 · 초대 · 접수**이고, **알리는 대상이 1건**인가 | 둘 다 ✅ → **원페이지 확정 (끝)** |
| **1** | 성격이 다른 **묶음(챕터)이 3개 이상**인가 | ❌ → **원페이지 확정 (끝)** |
| **2** | **한 장에 하나씩 넘겨 보는** 구성인가 | ✅ → **멀티 확정 (끝)** |
| **3** | 카드가 **35장 이상**인가 | ✅ → 멀티 / ❌ → 원페이지 |

### 3-B. 관문별 판정 기준

- **관문 0 · 「대상이 1건」** — 행사 1건짜리 초대장·예약 페이지는 페이지를 넘기게 하면 신청이 샌다 → 원페이지.
  ⚠️ **단 대상이 여러 건이면 여기서 끝내지 말고 다음 관문으로 넘긴다** — 행사 19건이 묶인 안내 책자, 매장 20곳 목록, 품목 50종 카탈로그는 목적이 「알림」이어도 원페이지가 아니다. **세는 것 = 행사 수 · 매장 수 · 품목 수 · 모집 건수.**
- **관문 1 · 「챕터 3개」** — 챕터 = **성격이 다른 묶음**(예: 회사 소개 / 제품 / 채용). 조립 레시피의 섹션을 성격별로 묶어 센다. **2개면 그냥 아래로 스크롤하는 편이 낫다.**
- **관문 2 · 「장면형」** — 룩북·포트폴리오·도록처럼 **한 화면에 하나씩 몰입해서 보는** 구성. **카드 수가 적어도 멀티**다(룩북은 한 장에 4~5장뿐).
- **관문 3 · 「35장」** — 조립 레시피를 펼쳐 **카드 수를 세어** 판정한다.

### 3-C. 왜 이 순서인가

- **관문 2가 3보다 앞이다** — 룩북(17장)·포트폴리오처럼 진짜 기준은 카드 수가 아니라 **「한 장에 하나씩 봐야 하는가」**다. 카드 수로만 재면 룩북을 놓친다.
- **35장의 근거** — 실제 원페이지들의 카드 수 중앙값이 **29장**. 이를 뚜렷이 넘는 지점이 35장이다.
- **애매하면 원페이지** — 멀티로 나누면 **카드가 오히려 늘어난다**(표지·목차 6장 ＋ 페이지마다 로고·복귀 헤더 2장 = **6 ＋ 2 × 페이지 수**). 13페이지로 나누면 그것만 30장이다. 나눠서 얻는 게 이보다 크지 않으면 원페이지가 낫다.
