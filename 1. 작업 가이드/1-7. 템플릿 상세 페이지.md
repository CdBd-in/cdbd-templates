# 템플릿 상세 페이지 콘텐츠

사용자가 `/templates/{slug}` 상세 페이지에서 보게 될 정보 = **카탈로그 메타데이터**. 사용자가 "템플릿 사용하기" 버튼을 누르기 전에 마주하는 첫 인상.

> 실제 페이지 제작(에디터 작업)은 [[1-6-1. CdBd 에디터]] 참조.

## ✍️ 작성 원칙

### 카테고리 선택
- 5종 카탈로그 중 1개. 템플릿의 **주요 사용처**에 따라 결정.
- 두 카테고리 사이에서 망설인다면 → 사용자가 검색 시 어떤 키워드로 들어올지 기준으로 판단.

### 🆔 슬러그 명명 규칙

어드민 등록 시 슬러그는 **어드민 URL**에 그대로 노출됨.

- ✅ **영문 소문자 + 하이픈(-)만 사용**
- ❌ 한글·언더바(_)·점(.)·대문자·공백 모두 불가
  - 단, 기존 등록 슬러그(`buttery_moment`·`oak_table` 등)는 **그대로 유지** (호환성)
- ✅ 캠페인 의도를 **영문 직역**으로 짧게
  - 예: `attendance-full`, `recruit-rsvp`, `corporate-sales`
- 신규 등록 시 충돌 가능성 있으면 카테고리 약어를 prefix로 (선택)
- **🔑 상세페이지 슬러그 = 「신규 템플릿 기획 문서」의 슬러그를 그대로 (2026-06-24).** 4단계에서 만든 **라이브 예시 페이지의 slug(사용자가 임의 지정)와 혼동 금지** — 예: class-enroll의 예시 페이지 slug는 `millnbutter`였지만 **상세페이지·어드민 등록 slug는 문서 기준 `class-enroll`**. (예시 페이지 slug를 그대로 적었다 정정한 사례.)

> 출처: qna 카드 dossier §4 URL 정보 편집 페이지 제약과 정합.

### 제목 작성
- "**무엇을 위해, 무엇을 하는, 무엇이다**" 구조로 압축.
- 예: "프로모션 노출과 상담 신청으로 전환을 만드는 영업용 명함"
  - 무엇을 위해 = 프로모션 노출 + 상담 신청
  - 무엇을 하는 = 전환을 만드는
  - 무엇이다 = 영업용 명함

### 사용 성과
- **수치 포함** 권장 (예: 전환율 40%↑, 예약률 2배, 조회수 1.5만+).
- 추상적 표현 ❌ → "고객 만족도 상승" 대신 "재방문 의향 88%"

### 추천 대상 (2가지)
- 구체적인 페르소나로 작성. 직군/업종/상황 명시.
- 예: "오프라인 영업 빈도가 높은 보험설계사", "신규 고객 응대가 잦은 1인 살롱 원장님"

### 주요 기능 (2가지)
- 템플릿이 가진 **차별점**에 집중. "프로필이 있어요" 같은 당연한 기능 ❌
- 예: "QR 명함 저장으로 한 번 만나도 잊히지 않기", "프로모션 배너로 본업 상품 자연 노출하기"

## 📊 라이브 13개 분석 기반 텍스트·이미지 규칙 (2026-06-24 정착, 필수)

> `cdbd.in/templates` 라이브 상세페이지 13개(promotion·campaign·sales·intake·corporate·dental·portfolio·newarrival·recruit-rsvp·seminar·reservation·rsvp·personalized) 전수 분석 결과. **신규 상세페이지는 이 패턴을 반드시 따른다.**

### 📝 텍스트 패턴

| 항목 | 규칙 (분석 기반) |
|---|---|
| **제목** | **베네핏-led** = `[기존 방식 대신/넘어] + [정량 또는 정성 베네핏]`. 동사는 `~하기`·명사구로 끝. **기능명 나열 ❌ → 사용자가 얻는 결과(전환율·이탈률·참석율·시간 절감)로 시작**. `~대신/넘어` 대조 구문으로 기존 방식(종이명함·구글폼+엑셀·복잡한 홈페이지)을 깔고 우위 제시. 숫자 들어가면 가장 강함. 예: "복잡한 B2B 영업, 모바일 명함으로 실계약 전환율 40% 상승" / "여러 폼으로 받던 걸 한 페이지로" |
| **본문** | **1인칭 사용자 후기체(리뷰체)** — `~했어요/~줄었어요/~편해졌습니다`. 광고체 ❌. 구조 = **`[기존 페인 포인트] → [CdBd 도입] → [정량/정성 개선]`**. **3~5문장, 150~250자.** 가장 좋은 본문은 **구체적 도구명·상황(야근, 엑셀 병합, PDF 이메일, 블로그/구글폼/문자)을 묘사**해 공감 트리거 생성 |
| **사용 성과 라벨** | **무조건 "사용 성과"로 고정** (13/13 통일, 변형 ❌). 설명문 = **한 줄 + 후기체 + 숫자 1개 필수**(%·배수·건수·기간). 예: "상담 문의가 2배 이상 증가했어요" |
| **추천 대상** | 2~3개 체크리스트. **`~하는 경우/~할 때/~담당자·리더` + 직무+상황 조합으로 페르소나 못박기**. 추상적 "사업주" ❌ → "외부 폼 여러 개로 RSVP 받고 엑셀 합치는 인사팀" |
| **주요기능 제목** | 짧은 **베네핏/기능 명사구**, `~하기` 빈번. 베네핏-led |
| **주요기능 설명** | **2~3문장, 80~150자.** `~할 수 있어요` 친근체. 구조 = `[기능] + [사용자 편집 자유도/결과]`. **"직접 편집 가능"을 자주 강조**(텍스트·서체·간격·순서 등 — 템플릿 본질과 일치) |

### 🖼 주요기능 이미지 = 기능 특성별 "디자인된 이미지" (raw 크롭 ❌)

**핵심: 가공 없는 라이브 화면 크롭은 약함(소수·비추천). 표준은 디자인된 이미지** — "이 기능이 어떻게 동작하고 무슨 결과를 주는지"를 한 장에 증명(라이브화면 + 에디터/결과화면을 겹치거나 화살표·점선으로 연결). 가장 잘 만든 페이지(sales·recruit-rsvp·dental·corporate)는 전부 디자인형.

**기능 특성 → 이미지 유형 매핑:**
| 기능 특성 | 이미지 유형 | 예시 |
|---|---|---|
| **버튼/CTA·구매·연락처저장** | **(b) 폰화면 크롭 + 점선박스/커서/콜아웃 라벨**로 "여기를 누른다" 시각화 | promotion 카드버튼·newarrival 구매버튼 (점선+커서) |
| **폼/설문/Q&A** | **(d) 에디터 질문빌더 패널 합성** — 객관식/주관식 빌더 카드 겹쳐 "자유 구성" | intake·rsvp·promotion |
| **예약/출석/RSVP/알림** | **(d) 신청→확정→SMS 플로우 합성** (점선 연결선으로 체인) | dental(캘린더→예약완료→SMS)·recruit-rsvp(다크카드→알림톡QR) |
| **데이터/통계/행동분석** | **(c) 차트 + 스탯 콜아웃 / pill 태그** | sales(페이지뷰·클릭률 스탯+라인차트)·rsvp(파이차트+응답자) |
| **갤러리/포트폴리오/룩북** | **(a/d) 멀티 이미지 그리드/카드** | campaign 갤러리·portfolio |
| **디자인/테마/개인화** | **(f/b) 스와치 그리드·디자인패널·이름 콜아웃** | corporate 색상타일·seminar "황영기 회장님께" 이름 콜아웃 |

### D. 신규 등록 시 처리 규칙

**🗑️ 복제 시 삭제할 요소**
- **10회 사용 / ★4.9 배지** (235:10941) — 누적 사용량·평점 표시용. 신규 등록 시 데이터 없으므로 **삭제 상태로 복제**.

**📱 산출물 — 모바일 페이지 스크린샷 (필수)**
- 보드 우측 **패션룩북 프레임** (235:11001/11003/11005/11007) 영역에 들어가는 콘텐츠.
- **4단계에서 완성된 CdBd 라이브 페이지의 모바일 프리뷰 스크린샷**을 캡처해서 붙임.

## 🤖 6단계 어드민 등록 자동화 패턴 (2026-06-22 기록 / T01)

> 어드민 폼은 React(react-hook-form) + 영구 `<input type=file>` DOM 구조. **에디터(4단계)와 달리 파일 input이 DOM에 영구 존재**해서 `$B upload`가 그대로 동작한다. 전체 흐름 1회 검증(T01 recruit-rsvp, 2026-06-22).

### 표준 흐름
1. **로그인**: `cdbd-admin.vercel.app/login` → `$B fill` 이메일·비번 → 로그인 버튼 클릭. 자격증명은 vault 루트 `.env` (`CDBD_EMAIL`/`CDBD_PASSWORD`).
2. **신규 폼**: `cdbd-admin.vercel.app/template/templates/new?lang=ko`
3. **좌측 메타**: `$B fill`로 템플릿명·제목·슬러그·에디터ID, 카테고리 체크박스 클릭, 활성화는 기본 ON.
4. **우측 상세 정보**: 부제목 라벨·설명·본문 `$B fill`, 항목은 input fill 후 추가 버튼.
5. **스와이퍼 영역**: `데이터 추가` 버튼 → 모달에서 제목·설명·표시순서 + 아이콘·설명이미지 업로드 → 저장. 주요기능 개수만큼 반복.
6. **저장**: `템플릿 생성` → 목록 페이지로 리디렉션되면 성공. 편집은 `.../{uuid}/edit`.

### 자동화 함정·해결 (어드민 전용)

| 함정 | 해결 |
|---|---|
| **React form state — native setter 갱신 X** | 모달/폼 input은 **`$B fill`**(Playwright keyboard 시뮬레이션) 사용. native setter+dispatchEvent는 "값 입력해주세요" 에러. (4단계 에디터와 동일 원리) |
| **버튼 `$B click` multiple match 에러** | 같은 라벨 버튼(`추가`·`수정`·`데이터 추가`) 다수 → `$B click @eN` 대신 **`[...document.querySelectorAll("button")].find(b=>b.textContent.trim()==="추가"&&!b.disabled).click()`** JS 직접 호출 |
| **파일 input 위치 식별** (썸네일 vs 상세 / 아이콘 vs 설명이미지) | `input[type=file]`은 width=0(숨김) → **visible 조상의 `getBoundingClientRect().y`로 구분**. id 부여 후 `$B upload "#id" path`. 통상 Y 작은 게 상단(상세/우측), 큰 게 하단(썸네일/좌측·설명이미지) |

| **저장 성공 확인** | 토스트가 즉시 안 잡힐 수 있음 → 목록 URL 리디렉션 또는 검색(`제목으로 검색`에 제목 텍스트 입력 → 검색 버튼)으로 행 존재 확인 |

## 🎨 썸네일 배경색 산정 룰 (정착 2026-06-18 / T01)

**썸네일(thumb)의 배경색 = 페이지 포인트색(버튼색)의 _hue_를 가져오되, 채도를 크게 낮추고 명도를 높인 「연한 저채도 파스텔」로 만든다. raw 버튼색 그대로 ❌.** (2026-06-24 정정 — 레퍼런스 보드 [642:516](https://www.figma.com/design/oi8zIHLfy59O5zV8aysqq4/CdBd-%ED%85%9C%ED%94%8C%EB%A6%BF-%EB%93%B1%EB%A1%9D?node-id=642-516) 18개 썸네일 전수 실측 결과 모두 **부드러운 저채도 라이트 파스텔**)

**기준 톤 (HSL)**: 버튼색 hue 유지 · **S ≈ 15~30%** · **L ≈ 78~88%**. 거의 무채색에 가까운 파스텔.

**레퍼런스 실측 예시 (base RGB)**:
| 톤 계열 | 예시 (base) |
|---|---|
| 세이지/민트 | campaign `rgb(207,219,211)` · lookbook-offline `rgb(175,197,186)` · **milnbutter `rgb(200,222,219)`** |
| 연보라/페리윙클 | corporate `rgb(220,226,239)` · recruit-rsvp `rgb(201,186,246)` · promotion `rgb(168,177,210)` |
| 크림/피치 | dental `rgb(240,227,206)` · newarrival `rgb(249,209,167)` · b2b-contract `rgb(233,192,171)` |
| 뮤트 로즈/브라운 | personalized `rgb(201,188,189)` · portfolio `rgb(217,193,187)` · reservation `rgb(194,189,181)` |
| 블루-그레이 | sales `rgb(205,214,228)` · intake `rgb(208,221,227)` · seminar `rgb(235,237,240)` |

**dim 레이어(선택)**: 더 깊이가 필요하면 base 위에 **Black dim 10~15%**를 별도 레이어로(거의 절반은 dim 없는 단일 SOLID — dental·intake·sales·rsvp 등). ⚠️ 단일 SOLID에 pre-multiplied로 합치지 말 것(인스펙터에서 레이어 보이게).

```js
// 예: teal 액센트 → 연한 민트-세이지 단일 SOLID (milnbutter)
thumb.fills = [{ type: 'SOLID', color: { r: 200/255, g: 222/255, b: 219/255 } }];
// 깊이가 필요하면 + Black dim:  , { type:'SOLID', color:{r:0,g:0,b:0}, opacity:0.12 }
```

```js
phone.fills = [
  { type: 'SOLID', color: { r: 0.086, g: 0.086, b: 0.102 } },  // 페이지 bg 색 (다크 무드)
  { type: 'IMAGE', scaleMode: 'FILL', imageHash: '...' },        // 캡처 이미지 위에 얹음
]
```
1순위: source 노드 자체에 임시 SOLID 추가 후 export → 복원 (1회용)
2순위: 위처럼 캡처 rect에 SOLID + IMAGE 두 레이어 (영구, 사용자가 인스펙터에서 검수 가능)

기존 참고: [신제품 소개 주요기능-1 235:10965](https://www.figma.com/design/oi8zIHLfy59O5zV8aysqq4/CdBd-%ED%85%9C%ED%94%8C%EB%A6%BF-%EB%93%B1%EB%A1%9D?node-id=235-10965) (구매 버튼 연동) — 제품 카드 + dashed 버튼 강조 + 커서 아이콘.

### 🖼 화면 캡처 = 「부모 프레임 + 이미지 레이어」 구조 + 저대비 그림자 (2026-06-24 정착, 필수)

주요기능 이미지에 들어가는 화면 캡처(mockup·UI 캡처)는 아래 3원칙을 따른다. 핵심 목적은 **편집 자유도** — 템플릿 본질대로 사용자가 직접 수정 가능해야 함.

1. **이미지 "자체"로 박지 말고 = 부모 프레임 안의 이미지 레이어로 배치.**
   - 각 캡처를 RECTANGLE(IMAGE fill)로 만들어 **별도 부모 프레임(카드)의 자식**으로 넣는다. 부모 프레임이 **모서리·클립·그림자**를 담당, 이미지 레이어는 콘텐츠만.
   - 이유: 사용자가 프레임은 그대로 두고 **이미지만 교체·이동·리사이즈**할 수 있다. feature 프레임(360×300)에 IMAGE fill을 직접 주면 레이어 구분이 안 되고 교체 외 편집이 어렵다.

2. **별개 화면 = 별개 레이어 (한 이미지에 여러 화면 ❌).**
   - 일시 선택·예약 완료처럼 **서로 다른 화면이 한 장으로 합쳐진 캡처는 화면별로 분리**한다. 각 화면을 잘라 **각자 부모 프레임 + 이미지 레이어**로 둘 것.
   - 분리 절차: `download_assets`의 `rawImages`로 **원본** 받기 → 화면 사이 **흰 거터(세로로 균일하게 밝은 컬럼)** 위치를 찾아 crop → 두 화면을 **같은 크기**로 맞춰(공통 세로 범위 + 균일 패딩) `upload_assets`로 각각 업로드 후 이미지 레이어에 hash 적용.
   - ⚠️ `upload_assets`의 `nodeId` 자동 fill은 RECTANGLE에서도 실패할 수 있음 → POST 응답의 `imageHash`를 받아 **`use_figma`에서 `fills`에 직접 적용** (`{type:"IMAGE", scaleMode:"FILL", imageHash}`).

3. **저대비 그림자 (필수) — 배경과 명도 차이가 작은 캡처는 그림자로 띄운다.**
   - 흰/밝은 UI 캡처가 카드·페이지 배경(예: `#f6f6f8` 회색)과 명도 차이가 작으면 경계가 사라진다 → **부모 프레임에 Drop Shadow**.
   - spec: `radius 8 · color #000 12% · offset (0, 2) · spread 0 · Normal` (feature2 QR 카드 [331:36](https://www.figma.com/design/oi8zIHLfy59O5zV8aysqq4/CdBd-%ED%85%9C%ED%94%8C%EB%A6%BF-%EB%93%B1%EB%A1%9D?node-id=331-36)과 동일 톤) · 모서리 `radius 12` · `clip ON`.
   - 카드는 feature 프레임(clipsContent) 안쪽으로 **충분히 inset** — 그림자가 잘리지 않게 상하 ≥14px 여백 확보.

**적용 예 — milnbutter reservation `feature1`** ([626:555](https://www.figma.com/design/oi8zIHLfy59O5zV8aysqq4/CdBd-%ED%85%9C%ED%94%8C%EB%A6%BF-%EB%93%B1%EB%A1%9D?node-id=626-555)): 합쳐져 있던 「일시 선택 + 예약 완료」를 흰 거터(원본 1971px의 x=985, 정확히 50%) 기준으로 분리 → 각 화면을 동일 807×1569로 crop → **139×270 카드(흰 배경·radius 12·shadow)** 두 개로 27px 간격 나란히 배치. 각 카드 = `{화면명} preview` 프레임 + `{화면명} 이미지` 레이어.

## 🗣 카피 톤 가이드 (정착 2026-06-18 / T01)

상세 페이지의 **사용 성과·본문·추천 대상은 리뷰 형식의 구어체**로 작성.

| 슬롯 | 톤 |
|---|---|
| 사용 성과 | "...됐어요 / ...줄었고요" 같은 1인 사용자 후기 톤 |
| 본문 | "...였어요 / ...하고 있어요" 사용자가 자신의 경험을 회상하듯 |
| 추천 대상 | 기호(·) 대신 자연어로 풀어 쓸 것. "...이라면 잘 맞아요" / "...에게 추천해요" |

❌ 영업 멘트 톤 ("...로 해소합니다", "...한 페이지에 묶어")
✅ 사용자 후기 톤 ("...만 되면 늘 야근이었어요", "...로 바꾸고 나서는...")
